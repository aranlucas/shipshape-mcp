# Practice coverage and adoption

The live catalog is a separate private repository. Editing `catalog-seed` does not migrate it. Deploy support for new checks first, then review and copy the selected definitions into the catalog through its normal editing workflow. Never replace owner-authored instructions or exceptions wholesale. Existing check types keep their existing semantics.

## Added semantic checks

- `ci-required-checks`: no options. Reads `.github/workflows/ci.yml` at the evaluated commit and requires every static job name (explicit `name`, otherwise job ID) in the default branch's required status checks. Additional required checks are allowed. Missing CI, empty jobs and known missing requirements fail; unreadable protection, malformed YAML, dynamic names, strategies/matrices, reusable workflow calls and duplicate names remain unknown. Uses the existing classic branch protection API; ruleset-only protections are not resolved and unreadable classic protection stays unknown. Protection is refreshed even when the commit and catalog are unchanged. This establishes configured context names, not successful CI execution, trigger/filter correctness, bypass policy, or GitHub App identity. Deploy engine support before adopting the updated `single-ci-workflow` seed in the separate live catalog. Remediation adds the job names as required checks while preserving existing protections; Shipshape never writes repository settings. See [GitHub's required-check guidance](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
- `preferred-package-manager`: requires a root pnpm or Bun declaration, permits workspace packages to inherit it, rejects tracked npm lockfiles, and detects explicit npm/npx commands in package scripts, workflow run steps and composite actions. The declaration may use `packageManager` or `devEngines.packageManager.name`; conflicting declarations fail. Dependabot ecosystem names, registry URLs and prose are not scanned. Arbitrary shell scripts, Dockerfiles, hooks, computed commands and remote actions are outside this static check. Unreadable or malformed files and incomplete inventories remain unknown unless an observed violation proves failure.
- `pnpm-setup`: rejects `pnpm/action-setup` references, including full SHA pins, in workflows and tracked composite actions. `pnpm/setup` and Bun setup actions are accepted. This check does not require a pnpm action in Bun repositories or prove that installation succeeded. Both checks reuse the captured tree and existing 64-file/512-KB read limits. Deploy the evaluator before adopting the matching live catalog definitions.

- `vitest-test-script`: no options. Requires a non-empty `scripts.test` directly invoking Vitest in every tracked root or nested `package.json`, without language or directory exclusions. Supports direct npm, pnpm, Yarn, and Bun executable runners; help/version/list/setup commands fail. Script aliases and complex commands require review. Discovery uses the captured tree and existing 64-file/512-KB read limits. Unreadable or malformed manifests and incomplete inventories remain unknown unless a known manifest fails. A complete inventory with no manifests passes. Adopt the new seed practice after deploying engine support.
- `husky-lint-staged`: checks root local dependencies, Husky initialization through `prepare` or `postinstall`, nonempty inline or JSON/YAML tasks, and a failure-preserving hook invocation. Resolves common package-manager commands and package-script aliases with an eight-alias limit. Code-based or ambiguous configuration, custom installers/directories, unsupported shell preambles and CLI config/cwd/diff selectors stay unknown. Snapshots read recognized task files at the captured commit using the existing 64-file/512-KB limits; no repository code is executed. The executable bit on Husky 9 user hooks is not required. Passing establishes static evidence, not task quality, execution or machine-local Git hook activation. The live catalog is separate: deploy evaluator support before copying revised seed instructions through its normal editing workflow.
- `oxforge`: optional `directory` (default `.`), `minimumVersion` (default `0.2.0`). Checks the manifest's supported lower bound, a single discovered Oxlint entry point, inherited base/recommended policy and locally duplicated anti-slop plugin registrations. Reads relative JSON/JSONC inheritance at the captured commit with the existing 64-file/512-KB limits. Does not execute repository code. Unread, dynamic, cyclic, ambiguous and unresolved declarations remain unknown.
- `oxforge-format`: optional `directory` (default `.`). Reads the package manifest and `oxfmt.config.ts` at the captured commit. Accepts shared Oxforge format exports, static project overrides and the `format()` helper. Requires enabled `sortTailwindcss` when any dependency section declares `tailwindcss`, including catalog/workspace versions. Stylesheet paths remain project-specific. Static syntax is parsed with Acorn and its Svelte TypeScript plugin. Type-only imports and variable type annotations are accepted; type-only exports do not establish shared formatting. Dynamic code, mutations, other TypeScript constructs and unsupported wrappers remain unknown without execution. Missing files in a complete inventory fail; unread files remain unknown. Replace the formatter `file-matches` entry in the live Oxforge practice with this check after deploying support.
- `dependabot-grouped`: optional `path` (default `.github/dependabot.yml`). Checks version 2, directory declarations, npm/GitHub Actions entries sharing one group, wildcard patterns, and that group's one-PR limit. Other ecosystems remain unknown pending an appropriate evaluator. Security updates are not promised to fit the version-update PR limit.

Oxforge checks deliberately do not claim the active lint command ran, the lockfile resolved a range, every local override is justified, or arbitrary scripts are unused. In particular, passing shared inheritance must not be read as proof that all shared rules remain enabled. The formatter check establishes shared inheritance and Tailwind opt-in; it does not verify stylesheet contents or run the formatter.

## Repository settings practices

`appliesTo.visibility` optionally selects `public` or `private` repositories using inventory visibility. Omitting it preserves eligibility for both. Deploy this applicability support before adopting definitions that use it.

- `always-suggest-updating-pull-request-branches`: requires the repository API's `allow_update_branch` setting to be `true`. Disabled suggestions fail; undisclosed settings and failed reads remain unknown. It applies to non-archived, non-fork repositories regardless of language or visibility. Remediation is to enable **Always suggest updating pull request branches** under **Settings → General → Pull Requests**. See [GitHub's documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-suggestions-to-update-pull-request-branches). The existing setting evaluator already supports this seed; adopt it in the live catalog through its normal editing workflow.

- `allow-auto-merge`: requires `allow_auto_merge: true` for public, non-archived, non-fork repositories. Private repositories are `not_applicable`, regardless of account plan or setting, and receive no failure or score penalty. Disabled auto-merge fails for public repositories; undisclosed settings and failed reads remain unknown. Enable **Allow auto-merge** under **Settings → General → Pull Requests**. This repository setting is separate from the `dependabot-automerge` workflow practice. See [GitHub’s documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-auto-merge-for-pull-requests-in-your-repository).

## Evidence behind the defaults

- [Oxforge base policy](https://github.com/aranlucas/oxforge/blob/main/configs/base.json) keeps consistent-return and readonly-parameter rules off and centralizes anti-slop policy.
- [delivery-dash test aliases](https://github.com/aranlucas/delivery-dash/blob/main/tsconfig.test-paths.json) map `@/*` to source and `@test/*` to root tests. Its Vitest config keeps dedicated integration scenarios separate.
- [react-hook-form-mantine Vitest projects](https://github.com/aranlucas/react-hook-form-mantine/blob/main/vitest.config.ts) combine root unit tests with Storybook browser tests. A Playwright browser provider alone is not evidence that a standalone Playwright e2e config is missing.
- [ai-shopping-mcp CI](https://github.com/aranlucas/ai-shopping-mcp/blob/main/.github/workflows/ci.yml) uses Ubuntu and `pnpm/setup` with locked install. Building views before tests is an actual prerequisite, not a redundant deployment-provider build.
- [grocery-agent-mobile scripts](https://github.com/aranlucas/grocery-agent-mobile/blob/main/package.json) use Expo lint and an Oxlint Tailwind add-on. A native-framework exception must be explicit rather than silently replacing the native toolchain.

These were inspected on 2026-10-15. They are examples of specific decisions, not blanket certification of those repositories.

## Remaining checks requiring review or a future evaluator

The thirteen seed practices do not cover every engineering preference. The CI seed establishes file presence, a pnpm/setup reference, root contents-read permissions and required static CI job contexts on the default branch; it does not prove one CI workflow, appropriate Ubuntu/public versus private self-hosted runners, locked setup, or absence of duplicate install/cache/provider-build work. The Dependabot auto-merge seed checks file presence, not workflow safety or required-check enforcement.

The Vitest script check establishes the declared test command; it does not inspect test imports or prove tests pass. Root/package test placement, source aliases without `src` in imports, and standalone Playwright e2e paths/configuration still need dedicated semantic evaluators. Framework, native, generated, vendor and Storybook exceptions must be considered for those future checks. Preserve meaningful security, domain and clinical contracts; static text matching cannot establish behavior-focused test quality. Remove only independently proven unused scripts, never diagnostic tools just because CI does not invoke them.

Repository transfers, inaccessible installations, permission-denied reads and truncated inventories are availability problems. Do not turn them into missing-standard failures. The UI must keep unknown and pending results separate from failed checks.
