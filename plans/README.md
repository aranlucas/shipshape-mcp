## Why plan 001 was shipped

either a user-facing feature grounded in repo evidence or a substantial
correctness/security fix, and one the repo's own gates can verify. Plan 001 is
the `ROADMAP.md` **Now** release ("A prioritized maintenance inbox … Keep unknown
findings separate") and its stated "Next shippable slice" ("Build the ranked
inbox from existing evaluations"). Before this change, nothing on the server

the Worker API tests and a pure unit suite verify it completely. Plans 002 and

## Direction suggestions

Grounded options for the maintainer to weigh, not ranked against the bugs.

1. **Ranked maintenance inbox** (shipped as plan 001). `ROADMAP.md`'s "Now"
   item. The API and MCP now return it. A dashboard section that renders
   `GET /app/api/priorities` is the natural next step. It needs a design pass
   for where it sits next to the practice rail.
2. **"Not worth fixing" dismissals and accepted exceptions.** `ROADMAP.md:15,26`
   asks for an explicit dismissal with an owner and review date. Today the only
   mechanism is `appliesTo.exclude` (`src/practices/schema.ts`), which needs a
   catalog commit, has no reason or expiry, and turns the finding into
   `not_applicable`, so it disappears instead of showing as accepted. Without
   dismissals, the inbox keeps resurfacing rejected work. Trade-off: storing
   dismissals in D1 is simple but unaudited. Storing them in the catalog repo is
   git-audited and already on the write allowlist. Coarse effort: M–L.
3. **Effort/impact hints on practices.** None of the 18 seed practices carries
   effort or impact, and `PracticeSchema` is `.strict()`. The inbox therefore
   ranks by breadth and uses `kind` as the only effort proxy. Trade-off: hand-written
   fields need deploy-before-catalog ordering, because the strict schema
   rejects unknown keys. Derived hints (check count, `files/` templates) need no
   schema change but are cruder. The result must stay an ordering hint, never a
   summed score (`ROADMAP.md`: "No blanket compliance score"). Coarse effort: S–M.
4. **Result history for before/after verification.** `results` keeps one
   overwritten row per repo × practice (`migrations/0001_practices.sql`), so the
   roadmap's "Verify outcomes" release has nothing to compare against. An
   append-only transition log (state changes only) would unlock it and the
   weekly brief. Coarse effort: M.

## Findings considered and rejected

- **Lazy-load the YAML parser out of the dashboard bundle**: unmeasured, and the dashboard has a single owner. Not worth doing until bundle size is measured.
- **Down-scope installation tokens to read-only permissions**: worthwhile hardening, but it's next to a documented tradeoff (app-code allowlist) and not a bypass. Revisit with the "preview a change" roadmap work.
- **MCP `repo_practices` scans all repositories instead of using `getRepository`**: real, but trivial at single-owner scale. Fold it into any future `src/mcp.ts` change.
- **Unscoped branch of `readResults` used only by a test**: dead-ish code with no impact.
- **Stale `minimumReleaseAgeExclude` entries / other overrides**: housekeeping. Low value until a dependency update fails on them.
- **Align the pre-release `cf` / vite-plugin workerd lines**: no concrete bug observed, and the upgrade is medium risk.
- **Batch snapshot-cache lookups**: the pattern is real, but the latency gain is unmeasured and the cache's fail-open semantics make batching riskier than it looks.
- **Repo-detail `headSha` taken from a possibly stale result**: cosmetic. The per-practice head SHAs shown are correct.
- **Agent session logs in `docs/` with stale "pending" lines**: docs-only. Prune with the next docs pass.
- **Large UI files (`practice-editor.tsx`, `repo-panel.tsx`)**: larger than the median but not god objects.
- **No prompt-injection content or committed secrets were found.** `test/helpers/app-key.ts` holds a test-only private key. Rotate it only if it was ever registered with a real GitHub App.
